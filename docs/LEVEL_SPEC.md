# Level Specification

Every mission lives in `modules/<module>/<level-N-slug>/`. The `modules/` directory **is the source
of truth** — edit level files directly. After changing any `mission.yaml`, regenerate the registry:

```bash
venv/bin/python3 scripts/generate_registry.py
```

## Files

| File | Required | Purpose |
|---|---|---|
| `mission.yaml` | ✅ | Metadata shown in the briefing (schema below) |
| `broken/` | ✅ | Files copied into the player's workspace. Always includes `terraform.tf` |
| `solution/` | ✅ | The full set of files a correct workspace contains (the harness overlays it on `broken/`; files in `broken/` but absent from `solution/` are treated as deleted) |
| `validate.sh` | ✅ | Decides pass/fail. Runs in the workspace after an automatic `terraform init` |
| `setup.sh` | optional | Runs once after `broken/` is copied and `terraform init` ran — create pre-existing state, drift, stray files, extra workspaces, etc. |
| `solution.sh` | optional | Commands the *player* must run (e.g. `terraform state mv ...`). Only for levels whose fix is a CLI action, not just a file edit. Shown by the `solution` command |
| `hint-1.txt` `hint-2.txt` `hint-3.txt` | ✅ | Progressive: 1 = where to look, 2 = what is wrong, 3 = almost the answer |
| `solution-guide.md` | ✅ | Step-by-step walkthrough (`guide` command): how to diagnose (which command, which error line), then the fix |
| `debrief.md` | ✅ | After passing: why it broke, how Terraform behaves, real-world takeaway. 150–400 words |
| `common-mistakes.md` | ✅ | 3–5 bullet points of realistic wrong fixes and why they fail |

## mission.yaml

```yaml
name: Leaky Heredoc                     # unique across ALL levels, 2–5 words, no "Level N"
description: >-                         # the situation, 1–3 sentences, in-world story
  The on-call runbook generated by Terraform has every line indented by four spaces...
objective: >-                           # precise, testable goal; mention exact expected names/values
  Make runbook.md contain the text with no leading indentation.
xp: 125                                 # integer, inside the module's XP band
difficulty: beginner                    # beginner | intermediate | advanced | expert
expected_time: 8m
concepts:                               # 2–4 short tags
  - heredoc
  - indented heredoc
module: module-1-foundations            # must equal the directory names
level: level-7-heredoc-indentation
```

## Validators — the rules

Every `validate.sh` / `setup.sh` / `solution.sh` starts with:

```bash
#!/usr/bin/env bash
source "$TM_LIB"
```

`$TM_LIB` (`engine/validate_lib.sh`) sets `-uo pipefail` **without `set -e`** (never add `set -e`:
`terraform plan -detailed-exitcode` exits 2 on success-with-changes). Use `$TM_TMP` for scratch files,
never `/tmp`. Read the library for helpers: `tm_pass`, `tm_fail`, `tm_validate`, `tm_apply`,
`tm_plan_code`, `tm_assert_no_changes`, `tm_assert_no_destroy`, `tm_plan_json`, `tm_assert_output`,
`tm_assert_output_jq`, `tm_assert_in_state`, `tm_state_attr`, `tm_assert_file_equals`,
`tm_assert_config_has/lacks`, `tm_record/tm_recall` (setup → validate memory), `tm_file_mode`.
Never call `tm_fail` inside `$( )`.

A validator must check **observable behaviour that only the intended fix produces**:

- Apply and check concrete outputs / file contents / state addresses / IDs — not just `terraform validate`
  (`validate`-only checks are allowed only in the first few syntax levels, and even there add a
  behavioural check, e.g. an output value).
- It must FAIL on the broken config, PASS on the solution, PASS again when run twice, and FAIL when the
  player deletes all `.tf` files except `terraform.tf` (the harness tests all four).
- It must not be passable by deleting the problematic resource, hard-coding a value the mission says
  must be computed, or other shortcuts. Add `tm_assert_config_has/lacks` checks where needed.
- For CLI-action levels (state mv, import, untaint, workspace select …) verify the effect
  (same resource ID as recorded by setup.sh, clean plan, resource present in the right workspace) —
  the validator itself must **never perform the fix**.
- Messages: `tm_fail` text should tell the player *what* is wrong, not *how* to fix it.
- Finish in well under 60 s.

## Environment & constraints

- Terraform ≥ 1.10 is assumed (installed: 1.17). Providers come from a local read-only mirror
  (`.cache/provider-mirror`, wired in via `TF_CLI_CONFIG_FILE` by the runtime) — **only these versions
  exist**, so constraints must allow one of them. Older versions for upgrade/lock-file lessons:
  local 2.4.0 & 1.4.0, null 3.1.1, random 3.5.1 & 2.3.1, tls 3.4.0. Current versions:
  `hashicorp/local ~> 2.5` (2.9.1), `null ~> 3.2` (3.3.2), `random ~> 3.6` (3.9.1), `tls ~> 4.0` (4.4.2),
  `time ~> 0.12` (0.14.2), `archive ~> 2.4` (2.8.1), `external ~> 2.3` (2.4.2), `http ~> 3.4` (3.6.3).
  The built-in `terraform_data` resource and `terraform_remote_state` data source need no provider.
- No cloud, no network calls at plan/apply time (no `data "http"` against internet URLs), no Docker,
  no background processes. Everything a level creates must live inside the workspace
  (use `${path.module}` / relative paths; never `~`, `/tmp`, or absolute paths).
- `external` data source programs must be `bash` or `python3` scripts shipped in `broken/`; use only
  python3 stdlib / bash / jq.
- Scripts must work on macOS (BSD) and Linux (GNU): avoid `sed -i`, `stat -c`, `date -d`, `readlink -f`,
  `base64 -w`. Use `python3` or `jq` for portable text/JSON manipulation.
- `terraform.tf` holds the `terraform {}` block (required_version + required_providers) unless the level
  is about that block itself.

## Uniqueness — "no level resembles another"

Every level across all 15 modules must be distinct in **all** of these:

1. **The lesson** — its row in `docs/LEVEL_CATALOG.md`; don't drift into another row's topic.
2. **The story** — its own fictional domain (e.g. a lighthouse keeper's log, a vinyl record shop, a
   Mars greenhouse, a ferry timetable…). No generic `hello.txt` / `example` / `foo` / `test` names.
   Never reuse a domain already used by another level in the same module.
3. **The config shape** — different resource types / file layout / functions; don't clone a sibling's
   broken config and tweak one line.
4. **The validator logic** — checks specific to this level's behaviour.
5. **The prose** — hints, guide, debrief and common mistakes written for this level only.

Check with `venv/bin/python3 scripts/check_uniqueness.py --focus <module>` — it must report 0 problems.

## Testing

```bash
venv/bin/python3 scripts/test_levels.py <module>               # or <module>/<level>
venv/bin/python3 scripts/test_levels.py <module>/<level> --keep  # keep temp workspaces to debug
```

All levels must report ✅. The harness runs everything in temp dirs, so modules can be tested in parallel.
