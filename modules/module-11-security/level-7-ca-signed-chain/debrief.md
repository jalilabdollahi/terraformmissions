# Debrief — a chain is three agreements, not one resource

A working private PKI needs three things to line up. The CA certificate must declare itself a CA (basicConstraints `CA:TRUE`)
and be allowed to sign (keyUsage `Certificate Sign`). The leaf certificate must be signed by the CA's *private* key and must name the CA as its issuer.
And the verifier must trust the CA certificate. The `tls` provider makes each agreement explicit:
`tls_self_signed_cert` creates the root, `tls_cert_request` carries the leaf's public key and names, and `tls_locally_signed_cert` combines
the request with the CA certificate and CA private key.

Mixing up which key goes where is the classic failure: the plan and apply succeed because every argument is a valid PEM, and the
problem appears only when a client verifies the chain. That is why this validator uses `openssl verify` instead of trusting Terraform's
success message.

Two real-world notes. Keys and certificates generated by the tls provider live in Terraform state, so this pattern suits development and test PKIs,
or short-lived internal ones, rather than a production root: keep real root keys offline or in an HSM/KMS and let Terraform handle only
intermediate or leaf issuance. And keep the leaf `allowed_uses` minimal: a controller that only terminates TLS needs `server_auth`, not signing rights.
