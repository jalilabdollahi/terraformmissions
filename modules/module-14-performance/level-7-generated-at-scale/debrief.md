# Debrief — loops need stable keys

Three hundred copies of the same block are a maintenance bug waiting to happen: a typo in one row
number is invisible in review, and adding a section means touching the file in 10 places. `for_each`
over a map generated from data reduces the config to the rule (how a tag is built) and the data (the
seating plan).

The migration is where people get hurt. `local_file.seat_a_1_01` and `local_file.seat["a-1-01"]` are
different addresses, so a straight swap plans 300 destroys and 300 creates. For files that is noise;
for databases, load balancers or certificates it is an outage. `moved` blocks map each old address to
its new key so the existing objects are adopted. They cannot be generated by Terraform itself (no
loops inside `moved`), but a three-line shell loop writes them reliably, and the file can be deleted
after everyone has applied.

Two design rules fall out of this:

- **Choose keys that mean something and never change** (`a-1-01`, not a list index). A key derived
  from a list position changes when somebody inserts an item, and every following instance is
  replaced.
- **Check the plan before the apply.** `Plan: 0 to add, 0 to destroy` plus a list of moves is the
  signature of a safe refactor. Anything else means a key or a name is off.

Real-world takeaway: scale demands data-driven config, and a safe refactor is "new code + moved
blocks + a plan that proves nothing changes".
